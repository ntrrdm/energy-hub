# Логическая модель EnergyHub

Модель работает в браузере и сериализуется в `localStorage`. Это описание сущностей прототипа и предметных связей, а не схема промышленной БД.

## Сущности и атрибуты

| Сущность | Ключевые поля | Назначение |
|---|---|---|
| Portfolio | `id`, `name` (логический контейнер) | Набор площадок владельца; в коде сейчас представлен агрегированным набором `sites`, без отдельного объекта Portfolio |
| Site | `id`, `name`, `address`, `lat`, `lon`, `limit`, `objects[]` | Площадка, координаты, лимит и список её измерительных объектов |
| EnergyObject | `id`, `siteId`, `name`, `meter`, `limit`, `quality`, `hourly[]`, `hourlyGrid[]?`, `hourlyPV[]?`, `source` | Объект измерения и три раздельных почасовых ряда; `null` означает пропуск |
| Asset | `id`, `siteId`, `kind`, `power`, `capacity?`, `soc?`, `status`, `x`, `y` | Оборудование и его параметры для реестра и схемы |
| Connection | React Flow `source`, `target` и графические поля | Направленная связь на топологическом полотне; направление пока визуальное и не используется в балансном расчёте |
| TariffBand | `id`, `start`, `end`, `buy`, `sell` | Временной интервал тарифа и цены импорта/экспорта |
| Schedule | `id`, `days[]`, `start`, `end`, `limit`, `date?` | Календарное правило лимита. Правило на отдельную дату имеет приоритет над недельным |
| ServiceCatalogEntry | `id`, `name`, `description`, `scope`, `needs`, `widgets` | Статическое описание услуги, ожидаемого уровня и набора виджетов |
| ServiceLink | `id`, `service`, `scope`, `target`, `status`, `limit` | Конкретное подключение услуги к площадке, оборудованию или хабу; отделено от описания каталога |
| MaintenanceItem | `id`, `object`, `issue`, `status`, `time` | Локальная заявка с состояниями «Открыта», «В работе», «Закрыта» |
| EventItem | `id`, `time`, `title`, `detail` | Запись локальной истории действий |
| Role | `admin`, `owner`, `operator`, `building` | Переключаемый демонстрационный режим; серверной идентичности и ACL нет |
| View / query result | объект, период/контекст, текст результата | Представление интерфейса; результат запросов пока текстовый, запросы распознаются правилами |

## Связи и кратность

- Одна площадка содержит много `EnergyObject` и много `Asset` (1:N).
- Объект измерения принадлежит одной площадке (N:1).
- Рёбра `Connection` связывают два объекта `Asset`; один узел может иметь много связей (M:N через рёбра).
- Один вид услуги каталога может иметь много `ServiceLink`; одно подключение ссылается на один сервис и одну цель. Цель задаётся парой `scope` + `target`, хотя код пока хранит её двумя обычными строками.
- `MaintenanceItem` ссылается на один `EnergyObject`; у объекта может быть несколько заявок (1:N).
- `Schedule` и `TariffBand` применяются по времени к расчёту выбранной площадки; явной связи с `siteId` у них сейчас нет.
- `EventItem` — плоский список событий, без строгой ссылки на сущность-источник.

## Правила интерпретации

1. Ряды `Demand`, `Grid` и `PV` не смешиваются. При расчёте нагрузки на сети используется `Grid`; демонстрационная сумма потребления строится по `Demand`.
2. Отсутствующее измерение хранится как `null` и не должно трактоваться как нулевое значение.
3. Оборудование принадлежит площадке через `siteId`. Связь на схеме не доказывает реальный электрический поток; для физического баланса необходимы типизированные порты, направление, коэффициенты и правила потерь.
4. Лимит объекта, лимит площадки и лимит расписания — разные значения. Активный лимит расписания выбирается по дате, дню недели и часу; исключение по дате имеет приоритет.
5. Доступная мощность батареи оценивается как минимум номинальной мощности и ёмкости, умноженной на текущую долю SoC. Это упрощение, не физический диспетчерский алгоритм.
6. Параметры подключения услуги (`target`, `scope`, `status`, `limit`) не должны смешиваться с описанием шаблона. В текущем прототипе состав и требования шаблона заданы статически; автоматический подбор каналов реализован не полностью.
7. Роль определяет только клиентскую видимость действий. Она не подтверждает право доступа и не должна использоваться для реальной защиты данных.

## Автоматическое построение представления

Предполагаемые входы: тип цели, доступные ряды измерений, тип и состояние оборудования, сервисное подключение и его параметры. Статические карточки услуг описывают ожидаемые виджеты; `ServiceLink` хранит область и цель. Нынешняя реализация открывает объектный обзор или сценарий Peak shaving по типу выбранной услуги. Она не анализирует произвольный набор показателей и не генерирует графики на лету; это оставшееся ограничение прототипа.
